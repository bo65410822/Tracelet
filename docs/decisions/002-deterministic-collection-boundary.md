# 002：自动采集仅覆盖确定性信号

## 背景

通用 Android SDK 可以观察 Activity、Fragment、Looper、Choreographer 等系统信号，但无法可靠获知用户何时发起业务路由、网络请求何时构成页面数据完成，以及页面内容何时达到业务可用状态。用生命周期回调或 UI 静默启发式推断这些阶段，会产生看似精确但语义不稳定的数据。

## 决策

Tracelet 的默认自动采集能力只覆盖具有明确系统信号、稳定语义且可重复验证的指标。每个指标必须明确记录或说明计时边界，不能把 SDK 实际观察到的局部阶段命名为完整业务耗时。

页面能力在 MVP 中限定为 Activity/Fragment 默认页面标识，并为 Compose 显式接入预留接口。MVP 不自动采集“页面进入到首帧”或“页面进入到加载完成”：前者的真实进入起点可能是用户操作或路由发起，通用 SDK 无法完整观察；后者依赖网络完成和业务内容就绪定义。UI 静默、固定延迟和重绘次数不作为业务完成依据。

若未来确有完整页面耗时需求，由宿主通过显式 API 提供业务起点或完成点；这类数据必须与自动采集的系统阶段指标明确区分。

## 原因

Tracelet 的价值来自可解释、可复现的诊断证据。少采集一个不确定指标，优于输出无法证明边界的数据。该约束也能避免复杂启发式增加运行开销、误报和维护成本。

## 影响

新增采集器必须先证明信号来源、指标语义、宿主兼容性和可测试性。主线程卡顿、系统边界明确的启动阶段、慢帧等能力可以继续评估；依赖业务语义的页面加载、网络完成和内容就绪不进入默认自动采集范围。相关文档和事件字段必须使用实际观测边界命名。

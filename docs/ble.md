# BLE 设备到云端的数据传输架构

## 1. 文档目的

本文定义从 BLE 设备、Android App 到云端的数据采集与可靠投递架构，重点说明：

- 每一层负责什么、不负责什么；
- 各层成功、失败和 ACK 的准确语义；
- 数据如何排队、持久化、上传、重试和清理；
- 在弱蓝牙、弱网、进程重启和重复投递场景下需要维持的系统不变量；
- 当前 Tracelet BLE SDK 已实现的边界与后续演进条件。

本文不承诺无线链路永不丢包，也不把 GATT 写入成功、手机持久化成功和云端业务处理成功视为同一件事。端到端可靠性需要 BLE 设备固件、手机端和云端共同遵守协议。

## 2. 当前范围与前提

### 2.1 当前已实现

`tracelet-ble` 当前聚焦 BLE GATT 单设备、单连接：

- 扫描 BLE 和 Classic 设备；
- 建立 BLE GATT 连接；
- 发现 GATT Service 和 Characteristic；
- 按 Service UUID 与 Characteristic UUID 进行原始 `ByteArray` 读写和 Notify/Indicate 订阅；
- 串行管理连接状态和 GATT 操作；
- 通过连接 session 过滤旧连接的迟到回调；
- 处理连接和操作超时、断开与平台资源释放。

当前连接只支持 BLE GATT。Classic RFCOMM/SPP 等真实需求出现后再评估，详见 `docs/decisions/003-ble-connection-transport-scope.md`。

### 2.2 当前不保证

通用 BLE SDK 当前不保证：

- 自动理解厂商自定义 Characteristic 的业务含义；
- 自动推断命令格式、字节序、校验码或响应格式；
- GATT 写成功等于设备业务已处理；
- 没有设备端 ACK 协议时实现安全重试和最终一致性；
- 在没有真实数据规模、延迟预算和可靠性等级时预设固定队列或批处理参数；
- 直接负责本地数据库、WebSocket、Protobuf 或云端业务协议。

## 3. 总体分层

```text
BLE 设备
  ↓ Notify / Indicate / Read
BLE GATT 传输层（tracelet-ble）
  ↓ 原始 ByteArray
设备协议层
  ↓ 结构化消息 + messageId + 可靠性等级
本地 Outbox（有界持久化队列）
  ↓ 待上传批次
上传协调层
  ↓
WebSocket 传输层
  ↓ TLS
云端网关
  ↓ ACK
上传协调层提交本地状态并清理
```

### 3.1 BLE GATT 传输层

负责：

- 扫描、连接、服务发现和断开；
- 原始字节读写和通知订阅；
- Android 版本兼容和权限检查；
- 同一连接中一次只执行一个在途 GATT 操作；
- GATT 操作超时、取消、错误映射和资源释放；
- 连接 session 校验，阻止旧连接回调污染当前连接；
- 在跨异步边界时复制 `ByteArray`。

不负责：

- 业务消息编解码；
- 设备业务 ACK；
- 数据库写入；
- WebSocket 上传；
- 云端业务成功判定。

BLE 平台回调不得执行数据库 I/O、网络 I/O 或复杂业务解析。回调只完成必要复制和事件投递。

### 3.2 设备协议层

负责：

- 将原始字节解析为结构化业务消息；
- 编码设备命令；
- 定义消息边界、版本、字节序和校验规则；
- 必要时定义 `messageId`、分包序号、总包数、设备 ACK 和去重；
- 区分可重试命令与不可安全重试命令；
- 设备身份校验、认证和防重放。

这部分必须基于设备固件协议实现，不能由通用 BLE SDK 猜测。

### 3.3 本地 Outbox

Outbox 是待上传消息的可靠事实来源。若要求 App 进程被杀后仍可恢复，必须使用持久化 Outbox，不能只依赖内存队列。

负责：

- 在事务中写入待上传消息；
- 维护 `Pending / InFlight / Delivered / Failed` 状态；
- 保存稳定 `messageId`，重试时不得生成新 ID；
- 按可靠性等级和创建时间读取待上传批次；
- 在符合约定的云端 ACK 到达后标记完成或删除；
- 限制记录数、单条大小、总磁盘大小和保留时间；
- 进程重启后恢复未完成消息。

### 3.4 上传协调层

负责连接本地 Outbox 和 WebSocket，但不实现底层 Socket：

- 从 Outbox 拉取有界批次；
- 管理单批次在途状态、ACK 超时和有限重试；
- 根据网络可用性与应用生命周期决定何时上传；
- 断线后将未确认批次恢复为可重试状态；
- 收到 ACK 后提交 Outbox 状态；
- 对长期失败提供可观察结果，不进行无限重试。

### 3.5 WebSocket 传输层

负责：

- 建立和维护 WebSocket/TLS 连接；
- 鉴权和 token 刷新；
- 发送、接收和连接状态通知；
- 使用有上限的指数退避与随机抖动重连；
- 约束单 Frame 和发送缓冲大小；
- 不在网络回调中执行复杂业务或数据库操作。

WebSocket/TCP 已提供连接内的可靠有序传输，但断线时无法单独判断远端是否已经处理某条消息。因此，需要业务层 ACK 和服务端幂等来解决“结果未知”问题。

## 4. 标识与状态模型

不同层的标识不能混用：

| 标识 | 生命周期 | 用途 |
|---|---|---|
| `connectionSessionId` | 一次 BLE 或 WebSocket 连接 | 过滤旧连接的迟到回调 |
| `messageId` | 一条完整业务消息 | ACK 关联、去重和幂等 |
| `packetIndex` / `packetCount` | 一条消息的分包过程 | BLE 分包与组包 |
| `uploadBatchId` | 一次云端上传批次 | 批次 ACK 与重试 |

连接 session 结束不等于消息失败。待上传消息是否保留，由 Outbox 和可靠性策略决定。

### 4.1 BLE 连接状态

建议连接阶段保持可解释：

```text
Idle
  → Connecting
  → DiscoveringServices
  → Ready
  → Disconnecting / Disconnected
  → Failed / Timeout
```

只有当前 `connectionSessionId` 对应的回调可以修改连接状态。一个连接 session 最多产生一个终态，终态后迟到事件必须被忽略。

### 4.2 消息投递状态

```text
Pending
  → InFlight
  → Delivered
  ├→ Pending（可重试失败或结果未知）
  └→ Failed（不可恢复或超过重试上限）
```

`InFlight` 不代表云端已经处理，只表示消息或批次已提交到当前传输连接。

## 5. ACK 层级与成功语义

系统中至少存在四种不同的“成功”：

| 层级 | 成功含义 | 不保证 |
|---|---|---|
| GATT 写回调成功 | Android 蓝牙栈完成本次写操作 | 设备业务已解析或执行 |
| 设备协议 ACK | 设备按协议确认收到或处理消息 | 手机已经持久化、云端已收到 |
| 手机持久化成功 | 消息已写入本地 Outbox，可在进程重启后恢复 | 云端已收到或处理 |
| 云端 ACK | 由协议定义：已接收、已持久化或已处理 | 不应由客户端自行猜测 |

协议必须明确每种 ACK 的语义。若设备收到手机 ACK 后会删除本地数据，则手机 ACK 的发出时机必须与产品可靠性目标一致：

- 要求进程崩溃后不丢：手机持久化成功后才 ACK 设备；
- 允许少量实时采样丢失：可先 ACK 再异步处理，但必须在契约中标明。

云端 ACK 也必须明确表示“网关收到”“已持久化”还是“业务处理完成”。只有达到产品要求的 ACK 层级后，Outbox 才能删除数据。

## 6. 设备端可靠传输

设备应用层 ACK 不是手机 SDK 单方面可以完成的能力。若要求可靠重试，设备固件必须共同支持：

- `messageId`；
- 分包序号和总包数；
- 重复包和重复消息去重；
- 组包缓存上限与超时；
- ACK 的准确语义；
- 协议版本和兼容策略；
- 命令幂等性或幂等键。

对于开锁、支付、启动设备等有副作用命令，没有幂等和去重保证时不得自动重试。重试必须复用原 `messageId`，不能把同一业务动作伪装成新消息。

当前通用 GATT 层只承诺原始操作结果，不承诺设备业务最终一致性。

## 7. 队列、背压和容量

### 7.1 不绑定具体队列实现

架构要求的是“有界队列”，不是必须使用环形队列。环形队列适合固定内存和高频 FIFO，但不提供进程重启恢复。具体实现根据可靠性要求选择：

- 内存有界队列：低延迟、允许进程退出时丢失；
- 持久化 Outbox：需要恢复和可靠投递；
- 内存前置缓冲 + 持久化 Outbox：在有明确性能证据时采用。

### 7.2 必须配置的边界

每层至少明确：

- 单条消息最大字节数；
- 队列最大条数和最大字节数；
- 批次最大条数和最大字节数；
- 最大等待时间；
- 最大重试次数或最大总重试时长；
- 本地存储总量和保留时间；
- 队列满时的可观察行为。

### 7.3 可靠性等级与溢出策略

建议按数据类型选择策略：

| 等级 | 典型场景 | 队列满时策略 |
|---|---|---|
| Critical | 有副作用命令、不可丢事件 | 持久化；失败时显式返回 `QueueFull`，不得静默覆盖 |
| Normal | 普通诊断事件、状态变化 | 有界持久化与有限重试，可按保留策略清理 |
| Sampling | 高频传感器采样 | 允许丢最旧、合并或降采样，并统计丢弃量 |

当生产速率长期高于消费速率时，任何队列都会满。系统必须执行预先定义的降级策略，不能依赖无限内存。

## 8. WebSocket 上传与批处理

### 8.1 重连

建议采用指数退避并增加随机抖动，例如：

```text
baseDelay × 2^attempt，限制最大间隔，并加入随机 jitter
```

同时必须设置最大重试次数或最大总时长。鉴权失败、协议不兼容等不可恢复错误不应继续重试；网络不可用时应等待系统网络状态变化，而不是空转。

### 8.2 批处理

批处理不是为了减少 TCP 握手或普通 HTTP Header。WebSocket 建立后不存在每条消息重新握手。批处理主要减少：

- WebSocket Frame 数量；
- 系统调用和序列化次数；
- TLS record 与网络包碎片；
- 服务端消息调度次数。

批次应在以下任一条件满足时发送：

```text
达到最大等待时间
或达到最大消息条数
或达到最大字节数
```

移动端使用受业务延迟预算约束的毫秒级窗口，不承诺微秒级调度。例如可从 20–100 ms 起步，通过真实负载测试调整。

### 8.3 ACK 粒度

不要求所有数据逐条 ACK：

- 关键业务命令：消息级 ACK + 幂等键；
- 普通诊断与遥测：批次 ACK；
- 可丢高频采样：可无 ACK，或周期性确认水位。

ACK 粒度应由可靠性目标、延迟和吞吐共同决定。

## 9. 序列化与协议演进

Protobuf 可以作为候选格式，但不是未经验证的必选项，也不预先承诺固定压缩比例。应使用真实代表性 payload 对 JSON、Protobuf 或其他二进制格式进行基准测试，比较：

- 编码后字节数；
- 编解码 CPU 和内存；
- 批处理后的收益；
- schema 演进和调试成本。

若使用 Protobuf，必须定义：

- schema 版本；
- 字段号永久稳定；
- 新增字段保持向前/向后兼容；
- 枚举未知值处理；
- 删除字段使用 `reserved`；
- App、设备固件和云端的升级/回滚兼容窗口。

不要在没有真实业务协议前，把某一种 payload 格式写进 BLE GATT 基础层。

## 10. 重试、幂等与结果未知

典型未知结果：

```text
客户端发送 messageId=100
→ 服务端已经处理
→ ACK 返回前 WebSocket 断开
→ 客户端无法判断远端是否完成
```

可靠方案必须同时具备：

- 重试沿用同一个 `messageId`；
- 服务端按 `messageId` 幂等去重；
- 明确去重记录保留期限；
- ACK 明确完成层级；
- 达到重试上限后进入 `Failed` 或 `UnknownOutcome`；
- 不可幂等业务不得自动重试。

TCP/WebSocket 的链路可靠性不能替代业务幂等。

## 11. 安全与隐私

### 11.1 BLE 侧

- 不以设备名称或 MAC 地址作为唯一可信身份；
- 根据设备能力选择 Bond、加密或应用层认证；
- 高安全场景使用挑战响应、防重放随机数和密钥轮换；
- 认证失败不得无限重试；
- 不自动连接未经身份确认的同型号设备。

### 11.2 手机与云端

- WebSocket 使用 TLS，并校验服务端证书；
- 认证 token 支持过期与安全刷新；
- 云端按租户、设备和用户执行授权；
- 敏感 Outbox 数据按业务要求加密；
- 日志不得记录完整 payload、密钥、token 或可识别隐私数据；
- 对消息大小、解析深度和批次大小设置上限，避免内存与解析攻击。

## 12. 线程、资源与生命周期

核心约束：

- BLE 平台操作通过专用串行执行上下文执行；
- 串行执行不等于平台异步操作已经完成，下一项 GATT 操作必须等待对应回调；
- WebSocket 回调只投递事件，不执行数据库和复杂解析；
- 所有外部 listener 异常必须隔离；
- 断开时完成或取消 pending 操作，并关闭 GATT；
- 永久释放组件时，先关闭平台资源，再取消负责清理的 scope；
- 所有 `ByteArray` 在进入异步队列、持久化或回调宿主前复制或转为不可变表示；
- 重连、超时和取消后，迟到回调必须校验连接代次。

## 13. 核心不变量

1. 同一 BLE 连接最多一个在途 GATT 操作。
2. 只有当前 `connectionSessionId` 的事件能修改连接状态。
3. 每次连接和每次操作最多产生一个终态。
4. `BluetoothGatt` 最终必须关闭，清理路径可重复调用。
5. BLE 回调线程不执行数据库和网络 I/O。
6. Outbox 有容量边界，溢出策略明确且可观察。
7. 一条消息重试时保持同一个 `messageId`。
8. 服务端按 `messageId` 幂等；没有幂等保证时不自动重试副作用操作。
9. 未达到约定 ACK 层级前，不从 Outbox 永久删除关键消息。
10. 所有重试有次数或时间上限，不无限快速重试。
11. BLE 连接状态与 WebSocket 连接状态独立维护。
12. GATT 写成功、设备 ACK、手机持久化和云端 ACK 是四种不同结果。

## 14. 分阶段落地

### 阶段一：BLE 原始传输

- BLE 单设备连接和服务发现；
- 按 UUID 原始读、写、订阅；
- GATT 单在途操作、超时、断开清理和迟到回调过滤；
- 原始 `ByteArray` 向上层交付；
- 暂不承诺设备业务 ACK。

### 阶段二：真实设备协议

在获得固件协议后增加：

- 设备身份和认证；
- 消息编解码；
- 必要的分包、组包和校验；
- 设备 ACK、去重、幂等和有限重试；
- 真机弱信号和断线测试。

### 阶段三：本地可靠队列

在明确“哪些数据不能丢”后增加：

- 有界持久化 Outbox；
- 容量、保留和溢出策略；
- 进程重启恢复；
- 消息可靠性等级。

### 阶段四：云端上传

在明确云端接口后增加：

- WebSocket 鉴权、状态和重连；
- 批处理和流控；
- 云端 ACK、服务端幂等和未知结果处理；
- 基于真实 payload 决定是否采用 Protobuf。

### 阶段五：端到端验证

覆盖：

- BLE 弱信号、断电、离开范围和迟到回调；
- App 被杀、重启、前后台切换和磁盘不足；
- WebSocket 断线、ACK 丢失、服务端重启和鉴权失效；
- 重复消息、乱序批次和服务端幂等；
- 生产速度长期大于上传速度时的背压与降级；
- 不同可靠性等级的数据丢弃和恢复行为。

## 15. 验收标准

- BLE 原始读写与订阅结果可观察，操作不会并发重叠；
- 旧连接和旧操作回调不会污染当前 session；
- SDK 内部异常和宿主回调异常不破坏资源清理；
- 关键消息在手机确认持久化前不会被错误标记为可靠接收；
- 队列和存储达到上限时执行明确策略，不发生无限增长；
- WebSocket 重连有限、有抖动、不会形成重连风暴；
- 重试复用 `messageId`，服务端可以幂等去重；
- ACK 语义可追踪，能区分链路写入、设备处理、本地持久化和云端处理；
- 序列化格式通过真实数据基准选择，schema 可以兼容演进；
- 核心状态机、Outbox 和上传协调逻辑可通过 deterministic fake 测试，不依赖真实等待。

## 16. 最终架构原则

这套架构复用的是“有界队列、稳定消息标识、ACK、幂等、超时和有限重试”等可靠消息语义，不是把 BLE 的实现直接平移到 WebSocket。

各传输层保留自己的约束：BLE GATT 面向小 MTU 和单在途异步操作；WebSocket 面向可靠有序流和断线后的结果未知；设备协议与云端协议分别定义业务成功。只有把这些边界分开，端到端链路才能做到可解释、可恢复和可验证。
